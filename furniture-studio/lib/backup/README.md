# lib/backup/ — экспорт/импорт каталога и настроек

> **Эта папка полностью самодостаточна.** Если ваша задача не касается
> резервных копий, экспорта или импорта — вам сюда не нужно, эти файлы не
> влияют ни на один другой модуль проекта. Точки входа снаружи: компонент
> `<BackupPanel />` на странице `/admin/settings`, три тонких Route Handler'а
> (Next.js обязывает физически держать их под `app/`), `lib/supabase/browser.ts`
> (нужен только этой панели) и миграция `0005_backup_staging_bucket.sql`.
> Все они — либо однострочные обёртки, либо инфраструктура для одной этой
> функции; ни один другой модуль их не использует.

## Что это и зачем

Резервная копия каталога (категории, товары, фото) и настроек сайта — на
случай сбоя базы или компрометации проекта. Формат — один `.zip`:

```
backup-2026-09-05.zip
├── manifest.json          — все данные таблиц (см. types.ts)
└── images/
    ├── works/...           — файлы из бакета Storage "works" (те же пути, что storage_path/image_path в БД)
    └── site/...            — файлы из бакета "site" (логотип, favicon, og-картинка)
```

`contact_requests` (заявки клиентов) в бэкап **намеренно не входят** — это
персональные данные с отдельной логикой хранения, а не конфигурация сайта.
Пароль администратора тоже не входит — им управляет Supabase Auth отдельно.

## Файлы

- `types.ts` — формат `manifest.json` (zod-схема `backupManifestSchema`) и версия формата (`BACKUP_FORMAT_VERSION`). Не помечен `server-only` — типы нужны и клиентскому `BackupPanel`.
- `manifest.ts` — читает все нужные таблицы из Supabase и собирает объект `manifest.json`. Ничего не знает про Storage/файлы.
- `export.ts` — берёт `manifest.ts`, докачивает связанные файлы из Storage, упаковывает всё в zip. Две функции: `buildBackupZip` (весь zip в памяти как Buffer — для письма) и `buildBackupZipStream` (Node-стрим — для скачивания из браузера, см. ниже почему это два разных пути).
- `import.ts` — разбирает загруженный zip, валидирует через `backupManifestSchema`, восстанавливает данные (`restoreFromZip`). Два режима — см. ниже.
- `email.ts` — отправляет готовый zip вложением на почту через Resend (используется только автобэкапом по расписанию).

Плюс `lib/supabase/browser.ts` — клиентский Supabase-клиент, которого в
проекте не было до этого модуля. Он нужен только для одной вещи: чтобы
`BackupPanel` мог загрузить архив восстановления прямо из браузера в Storage,
а не через тело серверной функции (см. следующий раздел).

## Почему архив грузится в обход тела серверной функции — это НЕ лишняя сложность

У serverless-функций на Vercel есть жёсткий лимит **4.5MB** на тело и запроса,
и ответа — его нельзя поднять никакой настройкой `next.config.mjs` (заданный
там `serverActions.bodySizeLimit` тоже не спасает: это лимит самого Next.js,
а платформа Vercel режет запрос ещё до того, как он дойдёт до кода). Каталог
с реальными фото почти гарантированно больше 4.5MB, поэтому:

- **Экспорт** отдаётся не единым `Buffer`, а Node-стримом
  (`buildBackupZipStream` → `Readable.toWeb` в `export/route.ts`) — стриминг
  ответа не подпадает под этот лимит.
- **Импорт** вообще не проходит телом запроса к нашему API. `BackupPanel`
  сначала грузит .zip напрямую в приватный Storage-бакет `backups` (сессия
  браузера синхронизирована с серверной через `@supabase/ssr`), и только
  путь к загруженному файлу (короткая JSON-строка) уходит в
  `POST /admin/api/backup/import`. Сам Route Handler скачивает файл из
  Storage уже server-to-server — это исходящий вызов, а не входящее тело
  запроса, лимит на него не действует. Staging-файл в бакете `backups`
  живёт только на время одного импорта и удаляется сразу после обработки
  (успешной или нет) — см. `finally` в `import/route.ts`.
- Бакет `backups` **не публичный** (в отличие от `works`/`site`) — создан
  отдельной миграцией `0005_backup_staging_bucket.sql`.

## Два режима импорта — это осознанный выбор, не два способа одного и того же

- **`add`** («добавить как новые») — категории и товары из архива вставляются
  с новыми id, ничего не удаляется и не перезаписывается. Настройки сайта,
  меню и способы связи в этом режиме **не трогаются и не дублируются** —
  это синглтон-конфигурация, а не каталог, дублировать её незачем.
- **`replace`** («полностью заменить») — необратимо удаляет текущий каталог и
  подставляет архив с исходными id, обновляет настройки/меню/связи на месте.
  Вызывающий код (Route Handler `import/route.ts`) обязан взять явное
  подтверждение у администратора ДО вызова `restoreFromZip(..., 'replace')` —
  сама функция никаких дополнительных вопросов не задаёт и просто выполняет.

## Известные ограничения (осознанные, как и остальные trade-off'ы в README.md)

- **Импорт не транзакционен.** Supabase JS клиент не даёт настоящей
  многотабличной транзакции без отдельной Postgres-функции (RPC), которой в
  проекте пока нет. Если импорт упадёт на середине (например, оборвётся сеть
  между вставкой товаров и фото), в базе может остаться частично применённое
  состояние. Для одного администратора и нечастого использования это
  приемлемый компромисс, но при реальном сбое стоит проверить данные после
  импорта, а не считать его гарантированно атомарным.
- **Если файла фото не оказалось в архиве** (например, оно уже пропало из
  Storage на момент экспорта), импорт не падает целиком — такое фото просто
  пропускается, а его storage_path попадает в `skippedImages` в ответе,
  которое `BackupPanel` показывает администратору.
- **Секции главной страницы (`home_sections`).** Общая структура
  `content_json` — произвольная, но по факту картинку туда кладёт только
  секция `hero` (ключ `imagePath`, см. `types/domain.ts` → `HeroContent`).
  Экспорт/импорт умеет доставать именно это поле. Если в будущем в
  `content_json` других секций тоже появятся картинки — их нужно будет
  добавить явно в `export.ts`/`import.ts`, они не подхватятся автоматически.
- **Resend имеет лимит на размер письма** (вложения в base64 раздувают
  реальный размер примерно на треть). Если каталог разрастётся до сотен
  тяжёлых фото, еженедельный автобэкап на почту может перестать помещаться —
  тогда стоит либо сжимать фото при загрузке (отдельная задача, вне этого
  модуля), либо сменить канал доставки автобэкапа на файловое хранилище.
- **Замена (`replace`) не разбирает конфликты по слагам/уникальным полям** —
  она полностью очищает таблицы перед вставкой, поэтому конфликтов unique
  constraint по построению возникнуть не должно, если только архив сам не
  испорчен (два товара с одинаковым id и т.п.) — на этот случай и есть
  zod-валидация в `types.ts`, которая ловит структурные ошибки, но не может
  поймать полностью бизнес-логические (например, дубли slug внутри одного
  архива) — тогда вставка просто упадёт с ошибкой уникальности от Postgres,
  и `BackupPanel` покажет её как есть.

## Переменные окружения (см. `.env.example`)

`CRON_SECRET`, `RESEND_API_KEY`, `BACKUP_EMAIL_TO`, `BACKUP_EMAIL_FROM` — без
них ручной экспорт/импорт из админки продолжит работать, не заработает только
еженедельный автобэкап на почту (`app/api/cron/backup/route.ts`).
